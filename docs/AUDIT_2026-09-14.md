Owner's brief: wrong sequences, time overruns, repeats of the mistakes already ruled on, threats to the three
objectives (balance every year · keys tie the print · rollover intact). Four independent read-only audits; the
serious claims were re-read in the code before listing. Severity is mine.

## C. Time
1. HIGH agent/llm.py:57-118 — one LLM call can retry for ~60 min (10 attempts × 600 s socket timeout, raise
   only at attempt 5); `json()` multiplies by repair retries; nothing passes a run deadline. The Actions
   job's 180-minute limit is what actually ends a stuck run. → a run-level deadline inside the client.
2. HIGH workqueue.py:1078-1186 — the breaker counts exceptions (each up to an hour); COMPONENT/PLUG cards and
   re-deals ignore the deadline. → time-based breaker; drain everything after deadline + grace.
3. HIGH reader.py:50/401 — the one-call reader sends up to 1.6 M chars + images and retries the same payload.
4. HIGH stage1_read.py:439-565 — vision is cold every run on Actions: up to 144 chats per scanned document.
5. HIGH tables.py — 300 tables ≈ 100k tokens a call; a truncated reply re-sends the batch; no clock between
   batches. → batch by bytes (~40 kB), check the clock, fall back after the first failure.
6. MED sensecheck/investigate — up to 18 full repair reruns per line inside a 180 s finish margin.
7. MED gate.py:335 — the archive is reloaded from disk on every gate call; the model 3-5×.
8. MED run.py:279-359 — the guards re-evaluate the whole grid per popped write (measured 0.3 s each).
9. LOW render/queue/moveon costs, all seconds.
Measured on the real models: full-grid error scan 0.3 s, a card's candidates 0.09 s, headline deltas 1.8 s —
the deterministic parts are minutes at worst; the hour-breakers are the LLM calls without a clock.
